ARCHITECTURE SUMMARY:

User Login
    ↓
Backend creates JWT with role
    ↓
Frontend stores in localStorage
    ↓
ProtectedRoute checks allowedRoles
    ↓ (match) or (redirect)
    ↓
API call with Authorization header
    ↓
Backend middleware verifies JWT
    ↓
Backend checks role permission
    ↓
Query data filtered by ownership
    ↓
Response returned to frontend

═══════════════════════════════════════════════════════════════════════════════

KEY PRINCIPLES:

🔐 NEVER TRUST FRONTEND
   - Frontend checks are for UX
   - Backend always verifies
   - JWT token is signed and verified

🎯 PRINCIPLE OF LEAST PRIVILEGE
   - Each role gets minimum access needed
   - Teachers see only their classes
   - Learners see only their progress

🛡️ DEFENSE IN DEPTH
   - Multiple layers of protection
   - If one fails, others catch it
   - Fail securely (deny by default)

═══════════════════════════════════════════════════════════════════════════════

ROLE DESCRIPTIONS:

👤 LEARNER
   Can: View own progress, take quizzes, view lessons
   Cannot: Create classes, see other learners' data, manage users
   Database: WHERE user_id = {req.user.id}

🧑‍🏫 TEACHER
   Can: Manage own classes, view own students, create quizzes
   Cannot: See other teachers' classes, access admin settings
   Database: WHERE teacher_id = {req.user.id}

🔑 ADMIN
   Can: Everything - all users, all content, system settings
   Cannot: Nothing - full access by design
   Database: No filters (sees everything)
